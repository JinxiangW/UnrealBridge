# Generate-Usage-Doc

Use this when the user asks for:

- usage guides
- artist-facing docs
- handoff notes
- parameter sheets
- practical summaries of UE assets, tools, systems, materials, blueprints, data assets, or workflows

Do not write these like articles. Write them like operating notes.

## Target style

This style is:

- operation-first
- role-specific
- result-oriented
- low narrative

This style is not:

- a background explainer
- a design article
- a theory dump
- marketing copy

## Core rules

1. Start with directly usable facts.
2. Put parameters / fields / controls before theory.
3. Sort by usage flow, not implementation order.
4. Split by role when different people own different controls.
5. Explicitly mark controls the target user usually does not need to touch.
6. Use short lines and compact sections.
7. Troubleshooting should be `symptom -> check`.

## What to include first

Default order:

1. asset / tool / system path or name
2. input / output, if relevant
3. main parameter / field / control table
4. non-target-user or runtime-owned controls
5. modes
6. asset requirements
7. hookup / integration requirements
8. starter values or common presets
9. troubleshooting

Adjust section names to the asset type. For example:

- material: model / UV requirements
- blueprint tool: required actors / components / exposed variables
- data asset: required fields / valid value ranges
- editor tool: required selection / target folder / output path

## Table rules

For each parameter, field, or control, give only:

- name
- default value, if known
- what it changes

Then in a follow-up section, say how to tune or use it:

- bigger / smaller does what
- common values or range if known
- only works in which mode
- who owns it, if ownership matters

Do not mix internals into the table unless the user asked for implementation details.

## Role split

When one asset exposes controls for multiple roles, split them.

Examples:

- artist-facing controls
- TA / runtime controls
- programmer-owned controls
- debug-only controls
- generated or read-only fields

Say it directly:

- target users usually do not need to touch this
- driven by code / TA / runtime
- generated by the tool
- read-only reference data

Example:

```md
## CPD 参数

这两个参数是运行时驱动参数。
美术预览和调材质时一般不用手动管。
```

## Sorting rules

Default: sort controls by how the target user will actually touch them.

Examples:

- preview-heavy material docs: preview controls first
- runtime material docs: mode switch, look controls, then range controls
- editor tools: target selection, filters, output settings, execute action
- data assets: required fields first, optional tuning fields second, debug fields last

Do not sort by:

- node graph left-to-right order
- reflection order
- declaration order
- serialization order

unless the user explicitly asked for implementation order.

## Modes

Write modes as small operating blocks.

For each mode, include:

- switch values
- what it looks like / does
- what controls matter most

Template:

```md
### 连续模式

参数：
- `Foo = true`
- `Bar = false`

效果：
- ...

主要调：
- ...
```

## Requirements sections

When relevant, separate:

- model requirements
- UV requirements
- actor / component requirements
- asset reference requirements
- material hookup requirements
- runtime hookup requirements
- data field requirements

Say only what affects successful use.

Examples:

- must have usable `UV1`
- effect advances along `UV1.G`
- top material must connect the function result back into final color
- selected actor must include component `X`
- data asset field `Y` must not be empty

## Troubleshooting format

Keep it compact:

```md
没效果：
- 先看 `UseChargeProgress` 是不是开了。

方向反了：
- 改 `InverseUV`。
```

No long diagnosis trees unless the user asked for a full debug guide.

## Language rules

Prefer:

- nouns
- verbs
- defaults
- ranges
- mode limitations
- owner / role labels

Avoid:

- long motivation paragraphs
- "this is powerful / flexible"
- repeating the user's request
- implementation backstory
- broad system theory

## Good output shape

Good:

- "default is 0.8"
- "larger value makes the edge softer"
- "only affects discrete mode"
- "artists usually do not need to touch this"
- "generated by the tool; do not edit manually"

Bad:

- "this parameter provides a powerful way to..."
- "internally the graph cleverly uses..."
- "as we can see from the design..."

## Recommended skeleton

```md
# <AssetOrToolName> 使用说明

资源：
`...`

输入：
- `...`

输出：
- `...`

## 参数

| 参数 | 默认值 | 作用 |
|---|---:|---|

## 运行时 / 非当前岗位参数

...

## 参数怎么调

...

## 模式

### 1. 预览模式
### 2. 连续模式
### 3. 分段模式

## 资源要求

...

## 接入要求

...

## 常用起手值

...

## 常见问题

...
```

## When to not use this style

Do not force this format for:

- architecture docs
- root-cause writeups
- engine implementation notes
- API references that are already schema-shaped

Those should stay in their native style.
